## 2. 背景

观察到的失效模式：通过测试发现的 bug，修复往往草率——"看一眼为什么→派发修复"，导致弱 agent 治标不治本，bug 越修越多。根因有三条因果链：

1. **治标**：根因写得浅 → 修症状 → 同一错误机制在别处再次触发 = 新 bug。
2. **不去重**：一个根因被拆成多个 BUG → 多次修复，每次都可能引入副作用。
3. **边界失控**：无 forbidden 约束 → "顺手改"扩散 → 修复制造新 bug。

**重要前置事实（已核实）**：本项目的 bug 处理框架**已经相当成熟**，不是从零造：

- `bug_resolution` 相位机后半段（fix→targeted reverify→TR-012 全新 S7 轮）已强制"完整走 DV+QA+E2E"。
- `docs/reports/bugs/BUG-template.md` **已存在且成熟**：§3 已有 `Hypothesis|Evidence|Result(confirmed/rejected)` 假设表 + E2E 必带 trace/console/network 的要求；§4 已有四子字段 Closing Contract（Repair scope / Forbidden scope / Before-fix evidence / Retest contract）；§7 已有 `Canonical BUG / duplicate of` 声明位。
- canonicalBug JSON Schema（`internal/schema/assets/review-evidence.schema.json:45`）已有 `root_cause`(string) / `impact`(string[]) / `repair_scope`(string[]) / `forbidden_scope`(string[]) / `source_finding_ids`(string[]) / `same_contract_failure_count`(int)。

**真正的缺口很窄**，集中在 bug_resolution 的**前半段（investigation + bug_report_review）深度不足**，具体四点：

| 缺口 | 现状（已核实） | 本 REQ |
|:---|:---|:---|
| ① 无错误机制分类 | §3 "Accepted root cause" 是自由散文；canonicalBug `root_cause` 是 string——无法据此判断两 bug 是否同根因 | 加受控词表 `root_cause.mechanism` |
| ② blast radius 非结构化、且在事后 | §2 "impact" 是一个散文格；`impact.ComputeImpact` 只在 §5 当事后引用 | §2 升级为结构小表；impact-analysis **前移到调查期** |
| ③ 字段是"被动填写" | 现有字段齐全，但填了就过，无"填时逼自己再想一步"的提示 | 给各 § 加**自查钩子**（核心） |
| ④ 无机制反思位 | §7 是事件流水，无"什么让这类错溜进来" | 加一行机制反思沉淀位 |

认知：**字段早已齐全，缺的是把字段从"被动"变"主动逼问"。** 这是纯加钩子的演进，风险极低；且符合"模板教、门兜底、散文只指路"原则——bug-resolution skill 文案可净减少。

## 3. 目标

| 目标 | 衡量方式 |
|:---|:---|
| G1 填写 BUG-template 即完成深查 | 自食：1~2 个 bug（夹具/合成）走演进后模板，自查钩子确实逼出根因/范围/去重（§7 FR-008） |
| G2 错误机制分类支撑去重与系统性识别 | 同 mechanism+重叠 blast radius 的发现被强制做去重决定（FR-004） |
| G3 blast radius 前移定边界 | impact-analysis 在调查期产出，regression_scope 驱动重验宽度（FR-002/FR-005） |
| G4 兜底门防浅修/越界 | 对抗性测试：浅 BUG（无 mechanism/无 blast radius/审查者=执行者）在 acceptance 被拒；修复后 changed_artifacts 越边界被拒（FR-006/FR-007） |
| G5 文档净减少 | bug-resolution skill + bugfix-review 规则总行数下降（FR-009） |

## 4. 范围

范围内：

- 演进 `docs/reports/bugs/BUG-template.md`：保留现有结构，**插入**机制词表行（§3）、blast radius 小表（§2）、自查钩子（§2/§3/§4/§7）、机制反思位（新增 §8）。
- canonicalBug JSON Schema：新增 `root_cause.mechanism`（受控词表 enum）；`impact` 升级为结构化 `blast_radius{affected_paths, affected_evidence, regression_scope}`；存量 BUG 走 grandfather 兼容。
- 定义受控机制词表（FR-003），种子来自现有测试夹具（BUG-003/039/103）+ `review-evidence.examples.json`（**本仓库尚无真实 BUG 文件**，v1 为合成种子，待首个真实 bug 后回灌）。
- 兜底门：PTR-BUG-02 acceptance 要求 `mechanism∈词表` + blast_radius 非空 + 去重决定已填；PTR-BUG-05 要求 `change_impact.changed_artifacts ⊆ repair_scope 且 ∩ forbidden_scope=∅`。
- 复用 `same_contract_failure_count`：递增时触发**机制重查**（回 investigation 重定 mechanism），而非简单重试。
- 瘦身 `skills/bug-resolution` + `docs/rules/bugfix-review.md`：详述性散文→"填 BUG-template（字段即调查）；门兜底"。

范围外（defer）：

- 重设 `bug_resolution` 相位机结构（后半段 fix→reverify→全轮已足够，不动）。
- 任何 harness 实跑（同 REQ-040，已否决）。
- REQ-040 的 review/completion 内容 schema 工作（二者独立，可并行）。
- Playwright runner / 浏览器环境（同 REQ-040）。
- 把 mechanism 反思自动收敛成 rule/skill 的流水线（先人工定期收敛）。

## 6. 术语

| 术语 | 含义 | 禁止叫法 |
|:---|:---|:---|
| 错误机制（mechanism） | bug 的错误*类别*（如并发竞态、状态机守卫缺失），取自受控词表；是去重与系统性识别的键 | "原因"（根因是具体定位，机制是类别） |
| blast radius | 一次 bug 的影响范围：受影响路径/证据/验证维度 + regression_scope | "影响"（太泛） |
| regression_scope | 重验宽度：targeted/module/cross-module，由 blast radius 决定 | — |
| 自查钩子 | 模板字段内嵌的"填到这里时逼自己再想一步"的提示；是"模板教"的载体 | "checklist"（那是独立文档） |
| 浅修 | 治标/不去重/越界三类之一 | "改错了"（不精确） |
| 深查触发 | `same_contract_failure_count` 递增 ⇒ 强制机制重查，而非重试 | — |

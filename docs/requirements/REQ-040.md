## 2. 背景

当前验证门禁（`internal/qualitygate/evaluator.go`、`internal/verification/clean_round.go`）是**完整性 + 指纹 + 出处**门，不是**经验真实性**门：

- 评估器对一条证据只校验约 12 个信封字段（kind/status/generation/round/path/sha256/responsibility/produced_by/invalidated_by/subject_refs/conclusion）。`conclusion="pass"` 是**字符串匹配**（`evaluator.go:502` `containsString`），不被复核。
- `review-evidence.schema.json` 正式定义的只有 4 种记录（canonicalBug/changeImpact/targetedReverification/cleanRound）；`delivery_review / qa_review / e2e_review / document_review / completion_report` **无正式 JSON Schema**，内容层是机器不读的自由文本。
- 整个门禁路径的 `FileView` 只有 `ReadFile`（`evaluator.go:32`），**从不执行任何命令**。

后果一：一个"自信但错误"的 agent 写全证据信封、填 `pass`、附"看起来对"的截图，就能通过——因为测试是否真跑通、E2E 是否跳过负面用例、集成边界是否被 mock，机制层无法判定。

后果二（E2E 特有）：E2E 是"导航→交互→观察→断言→取证→判 pass/fail"的判断循环，且常常需要**迭代修改 Playwright 脚本**才能判定一次失败到底是**测试 gap**（脚本本身写错/选择器漂移/时序问题）还是**实现 gap**（代码真有 bug）。如果允许用 URL 直跳、直接写库造数据、或直调后端 API 来"完成用例"，就绕过了前端交互本身，E2E 退化为后端联调，失去验证意义。当前没有任何约束阻止这类捷径。

这两点合起来，正是目前仍需人在会话中持续把控、回拨状态的根本原因。

## 3. 目标

| 目标 | 衡量方式 |
|:---|:---|
| G1 堵住断言式 pass | 对抗性测试：伪造格式完整的 `pass`（无原始证据/无佐证）被新门拒绝（§7 FR-006） |
| G2 把验证粒度从"职责"细化到"用例" | 22-CASE 场景：缺 1 个 CASE 的原始证据/佐证 ⇒ round `incomplete`（§7 FR-004） |
| G3 不增加 harness 执行职责 | harness 全程不 exec 任何验证命令；证据由独立执行 sub-agent 产出、独立审查 sub-agent 佐证（§4 范围外明示） |
| G4 E2E 真交互 | E2E 必须由 Playwright 走前端交互完成；捷径（URL 直跳/直写库/直调 API）被守门拒绝（§7 FR-010） |
| G5 自食闭环 | 用本 REQ 产物对 harness 一个真实小改动跑通一轮 Delivery+QA（E2E 视环境可选）（§7 FR-007） |

## 4. 范围

范围内：

- 给 `delivery_review / qa_review / e2e_review / document_review / completion_report` 补正式 JSON Schema（canonical + `omitempty`）。
- 定义按验证种类的**原始证据清单**（raw-evidence manifest），其中 E2E 清单须满足 FR-010 真交互约束。
- 新增 `corroboration_record` 证据种类 + 独立审查者职责。独立性分两层：①**编排层**复用现有 team-manifest separation edge（保证审查者与执行者被分派为不同 agent 实例）；②**评估器层新增**跨证据 `producer_agent_id` 比对（先例 `applyDocumentPassIndependence`），校验"佐证 producer ≠ 被佐证原始证据 producer"。
- 把 `all_required_dimensions_passed` 升级到 **CASE_ID 粒度**（复用现有 `scenario-cases` 的 CASE_ID）。
- 新守卫 `backed_by_raw_evidence_and_corroboration`。
- **E2E 真交互约束**：必须 Playwright 走前端交互；禁止 URL 直跳/直写 DB/直调后端 API 作为完成手段；单 agent 单职责逐用例派发，允许迭代修改 Playwright 脚本以区分测试 gap 与实现 gap。
- 对抗性门禁测试 + 窄口径自食。
- **设计立场（owner 决策，依 `blueprint/L1-design-principles.md` 公理四）**：验证兜底层的 token 消耗是**显式定价的保险费**——一人一 E2E 用例执行、逐用例独立佐证为强制项，不从这里削减；优化方向是让每份 token 买更多确定性（机械预检先行、审查者批量激活摊薄开销），而非降低覆盖。

范围外（defer 到后续 REQ）：

- **harness 实跑任意验证命令**（已否决：E2E 是判断循环，harness 跑不了；且会让 harness 比问题更重）。
- **大规模证据字段瘦身（线 1）**：等自食数据再立项，避免拍脑袋砍。
- **`ci_green_record` 发布门（线 2c）**：单独立项。
- **Playwright/浏览器环境与框架本体**：依赖外部环境，本 REQ 只定义"E2E 原始证据清单 + 真交互约束"，不搭 runner、不重写框架。
- 单元/集成的 harness 强制实跑：本 REQ 不强制；仅预留"可选机械抽查"接口，不在守卫里开启。

## 6. 术语

| 术语 | 含义 | 禁止叫法 |
|:---|:---|:---|
| 原始证据（raw evidence） | 执行 sub-agent 跑用例时落盘的可校验原始产物（trace/HAR/截图/命令+退出码+日志等），按验证种类有固定清单 | "截图""报告"（这些是产物，非术语） |
| 佐证（corroboration） | 独立审查 sub-agent 产出的 `corroboration_record`，必须引用具体原始证据条目，结论 back 执行者的 pass | "复核""复审"（语义重叠，统一叫佐证） |
| CASE_ID 粒度 | 完整性门按场景包里的 `CASE_ID`（即 `scenario-cases.schema.json` 的 `case.id`）计数，而非笼统的 responsibility ID | "用例级""维度级"混用 |
| canonical 证据 | 经规范形序列化的 JSON，字节确定 → SHA-256 稳定 | "格式化 JSON"（不规范形不算） |
| 断言式 pass | 仅凭 `conclusion="pass"` 字符串即通过，无原始证据/佐证背书 | "假绿""假 pass" |
| E2E 真交互 | 用例必须通过 Playwright 驱动真实浏览器、经前端 UI 交互完成；交互事件（点击/输入/导航由 UI 触发）须体现在 trace/HAR 中 | "前端测试"（太宽） |
| E2E 捷径（禁止） | URL 直跳绕过点击流 / 直接写库造状态 / 直调后端 API 完成用例——任一即判非真交互 | "mock""seed"（这些有合法用途，不等于捷径） |
| 测试 gap vs 实现 gap | 一次 E2E 失败的归因：前者=脚本/选择器/时序问题（改测试），后者=代码真有 bug（修代码）。区分需迭代改 Playwright 脚本 | "测错了""写错了"（不精确） |

### 非功能（摘要）

性能——评估器新增校验不得使单次门评估超预算（沿用现有 quality-cycle budget）；可靠性——canonical 序列化保证指纹稳定，禁止引入 YAML/TOML 等无规范形格式进证据层；安全——即便本 REQ 不强执跑，也预留"验证命令允许清单"接口供后续；可维护——单一 JSON 格式，与现有 runtime/journal/manifest 生态一致。

## 2. P1 Findings

### S9-01：ChangeImpact commit 与 TargetedReverification 的顺序形成真实流程偏移

- **严重度**：P1
- **位置**：`internal/repair/runtime.go:614`、`internal/repair/runtime.go:711`、`internal/repair/evidence.go:81`
- **设计要求**：协议规定 `ChangeImpact create → ChangeImpact commit → TargetedReverification create → TargetedReverification commit`，见 `docs/agent-protocol.md:637-648`。Blueprint 要求 Impact 事务创建 TargetedReverification work package，见 `blueprint/L3-S9-repair.md:470-479`。
- **当前实现**：`CommitChangeImpact` 在切换到 `targeted_reverification` 前调用 `bindRequiredReverificationIDs`，要求 `required_reverification_ids` 已能解析到最终 TargetedReverification 文件。
- **问题**：当 required set 非空时，按文档操作会先 commit Impact，但 commit 会拒绝缺失的下游 Targeted 文件。操作者只能提前创建一个本应在 Impact commit 之后产生的文件，绕过正常顺序。
- **影响**：正常操作路径不可用；Impact 事务也没有真正创建 work package，只是消费预先存在的 artifact。
- **建议**：Impact commit 创建不可变的 re-verification obligation/work package；Targeted create/commit 后续再绑定最终证据。最终 Targeted artifact 应由单独 CAS 消费 obligation。

### S8-01：S8→S9 的人类审批证据仍是可选的

- **严重度**：P1
- **位置**：`internal/investigation/contract.go:24`、`internal/investigation/contract.go:160`、`internal/cli/investigation_command.go:1015`
- **设计要求**：S8→S9 是 Main/Architect 的 authority transaction，应绑定被批准的 Contract 内容和人类审批边界，见 `blueprint/L3-S8-finding-investigation.md:523-535`。
- **当前实现**：API 支持 `ApprovalHash` 和 `ApprovalEvidenceID`，但两者都 optional；生产 CLI 只提供 `--approved-by`，没有传入审批 hash 或 human-decision evidence。
- **问题**：当前生产路径只能证明某个字符串身份提交了批准，不能证明审批人实际审阅并批准了当前 draft 内容。代码虽然会写入 draft 的计算 hash，但该 hash 不是审批人确认的 hash。
- **影响**：拥有 CLI 调用权限的主体可以用自由字符串完成 Contract approval，削弱 S8→S9 的人闸。
- **建议**：生产入口强制 `ApprovalHash` + 与 `ApprovedBy` 同身份、同 revision、同 verb scope 的 `human_decision` evidence；CLI、schema、错误提示和测试统一接入。

### S8-02：Case baseline drift 只告警，不阻断 Contract approval

- **严重度**：P1
- **位置**：`internal/investigation/case_workflow.go:671`、`internal/investigation/case_workflow.go:782`、`internal/investigation/contract.go:119`
- **设计要求**：Contract approval 必须校验 Case revision、source Finding exact set 和 baseline，见 `blueprint/L3-S8-finding-investigation.md:525-533`。
- **当前实现**：Case revision 会比较当前 ReviewPlan subject digest 与 Case 的 `baseline_digest`，漂移后写入 `investigation_baseline_drift` 告警；但 `ApproveContract` 只执行 `requireRepairReadyCase`，不检查该告警，也不重新验证当前 baseline。
- **问题**：baseline 已漂移的 Case 仍可以生成 approved RepairContract 并进入 S9。S9 后续会记录自己的 session baseline，但不会恢复 S8 Finding/Case 证据与原始 S7 baseline 的一致性。
- **影响**：调查结论可能针对旧 subject，修复却在新 subject 上执行；authority chain 语义断裂。
- **建议**：存在 baseline drift 时拒绝 approval，要求重新 ingest/rebaseline；审批事务中重新加载当前 ReviewPlan、重算 digest，并将批准 hash 与该 digest 绑定。

### S10-01：S10 requirement/contract 覆盖分母仍可由 manifest 作者缩小

- **严重度**：P1
- **位置**：`internal/acceptance/manifest.go:312`、`internal/acceptance/manifest.go:456`、`internal/acceptance/manifest.go:659`
- **设计要求**：S10 应从 REQ、contracts、TASK Closing Contracts、S7 Claims、S9 ChangeImpact、changed paths 和 risk tags 冻结 finite inventory，且不能为了 PASS 缩小分母，见 `docs/agent-protocol.md:675-681`。
- **当前实现**：机器会要求 `requirement`、`contract`、`changed_path` 类别至少各有一行；changed paths 会与外部 baseline 交叉校验。但 requirement/contract 行的完整对象集合没有从 REQ、TASK、S7 Claim 或 Contract 自动重建。
- **问题**：只要提供一行自声明 requirement、一行自声明 contract，并覆盖所有机器可见 changed paths，manifest 就可能计算出 100% coverage，同时遗漏多个 AC、Closing Contract 或 Claim。
- **影响**：S10 的机器反捷径保证只覆盖 changed-path 分母，不能独立证明完整 acceptance universe 已冻结。
- **建议**：由 Runtime/Quality Gate 从权威对象生成 expected inventory 并与 manifest exact-set 比较；如果短期保留人工 T2，应明确把 S10 状态标为“机器地板通过、权威分母待人工核验”，不能把它当完整 PASS。

### RT-01：journal rotation 在“已截断、未清 marker”崩溃窗口可能永久阻塞 Runtime

- **严重度**：P1
- **位置**：`internal/runtime/store.go:2594`、`internal/runtime/store.go:2625`、`internal/runtime/store.go:2637`、`internal/runtime/journal_rotation_test.go:116`
- **当前实现**：rotation 顺序是 marker → archive → truncate active → clear marker。恢复逻辑在 active event 数量小于 `ArchivedCount` 时直接报错。
- **问题场景**：若 active 已成功截断为只剩 tail，但进程在清除 marker 前崩溃，恢复时 active 数量通常小于 `ArchivedCount`，代码进入“refusing partial-truncate”错误分支。marker 被保留，后续 Snapshot/Update 会反复失败。
- **测试缺口**：现有测试覆盖 marker/archive 写入后、active 尚未截断的崩溃场景，但没有覆盖 active 已截断、marker 尚未清理的场景。
- **影响**：长生命周期 Runtime 达到轮转阈值后，单个崩溃窗口可能使 S7～S10 所有 Runtime 写入和读取永久受阻，直到人工 reconcile。
- **建议**：恢复逻辑应识别“active 已是合法 tail”的状态，校验 tail sequence/hash 后清理 marker；补充截断后崩溃测试，并验证 state/journal pair 和 marker 清理的幂等性。

## 3. P1/P2 Evidence provenance Finding

### EVID-01：外部 execution evidence 只有 scheme 格式校验，没有真实性绑定

- **严重度**：P1/P2（取决于 `scheme://` 是否被当作可信验收证据）
- **位置**：`internal/evidence/semantic.go:47`、`internal/evidence/semantic.go:87`、`internal/repair/evidence.go:180`、`internal/repair/runtime.go:901`
- **当前实现**：所有包含 `://` 的 ref 都被当作外部 execution anchor，非空即可通过；不要求 Runtime evidence index、artifact SHA、执行收据或 connector attestation。
- **问题**：例如 `test://fake` 可以满足 S8 hypothesis/result 或 S9 targeted assertion 的外部证据引用要求。Targeted PASS 的结构校验不能证明外部执行确实发生过。
- **影响**：若外部 ref 被用作因果闭合或 targeted PASS 的唯一证据，攻击者可以用格式正确但无事实来源的字符串完成闭环。
- **建议**：为每种外部 scheme 提供注册的 verifier/connector，要求 execution receipt、主体、时间、输入 digest、输出 digest 和签名/可信来源；无法 attestate 时应返回 UNKNOWN 或 BLOCKED，而不是 PASS。

## 4. P2 Findings

### S7-01：本地 `path:` evidence ref 可省略 SHA256

- **严重度**：P2
- **位置**：`internal/review/submit.go:677`、`internal/review/submit.go:761`
- **当前实现**：`path:<file>` 不带 `#sha256=` 时只校验文件存在且为普通文件；只有显式携带 digest 才读取并比对内容。
- **问题**：Result 消费后，文件内容可以改变，而该 path ref 本身仍没有内容锚点。虽然 product subject 和 E2E digest 有其他 freshness 检查，但普通 verification artifact 仍可能漂移。
- **建议**：要求所有本地 path evidence 显式带 SHA；或者统一先注册为 Runtime evidence，再只允许 `runtime:<evidence-id>` 引用。

### S8-03：S8 hypothesis/result 的 evidence 校验在读取 Runtime 失败时存在 fail-open 前置检查

- **严重度**：P2
- **位置**：`internal/investigation/case_workflow.go:141`、`internal/investigation/case_workflow.go:192`
- **当前实现**：注册 Hypothesis 或提交 Result 时，若临时 Snapshot 失败，代码会跳过 evidence attestation 前置检查。
- **缓解因素**：后续 `updateCaseRevision` 会再次读取 Runtime，正常情况下仍会失败，因此当前更像错误路径一致性问题，而不是稳定的直接绕过。
- **建议**：读取 Runtime 失败必须 fail-closed；不要以“跳过预检查、交给后续流程”替代明确错误，避免未来后续流程变更后形成真实绕过。

### S8-04：detection gap evidence refs 的语义校验弱于 hypothesis/result refs

- **严重度**：P2
- **位置**：`internal/investigation/contract.go:1104`、`internal/investigation/contract.go:1157`
- **当前实现**：detection gap 主要校验类型和 refs 非空；hypothesis/result 的新 evidence attestation 并未统一覆盖所有 detection-gap refs。
- **问题**：因果闭合要求 detection gap 存在，但 gap 引用本身不一定能解析到当前有效证据或可信外部收据。
- **建议**：所有进入 causal closure 的 evidence refs 使用同一套 current-generation、status、round、SHA 和外部 attestation 规则。

### S9-02：Impact 的部分语义字段仍是声明性字段，未完全驱动机器决策

- **严重度**：P2
- **位置**：`internal/repair/model.go:227`、`internal/repair/model.go:268`
- **当前实现**：`RetainedEvidenceIDs`、`RecoveryEvidence` 等字段进入 ChangeImpact/Targeted 模型；`InvalidatedEvidenceIDs` 和 `SupersededEvidenceIDs` 已被消费，但 retained/recovery 的逐项语义验证和后续消费不完整。
- **问题**：schema 可以要求字段存在，但 Runtime 不一定验证其原因、影响范围或后续状态，导致 rich impact 与实际 evidence ledger 可能脱节。
- **建议**：为四类 disposition 建立统一的 decision consumer：每项都要有 reason、scope、source、target state 和后续 gate；未消费字段应暂时从 schema 删除或明确标为 audit-only。

### S10-02：S10 CLI manifest validate、evidence register 和 Quality Gate 使用的校验强度不一致

- **严重度**：P2
- **位置**：`internal/cli/s10_command.go:95`、`internal/acceptance/manifest.go:597`、`internal/qualitygate/evaluator.go:447`
- **当前实现**：CLI 与 evidence registration 使用 `ValidateForOutcome`，不传入外部 changed-path baseline；Controller 的 Quality Gate 后续才调用 `ValidateForOutcomeWithBaseline`。
- **问题**：同一份 manifest 可能先被 CLI/registration 报告为 valid，随后在正常 gate 中因 changed-path denominator 不完整而变成 UNKNOWN/NOT_READY。
- **建议**：CLI、注册前校验和 Quality Gate 共享同一个 baseline-aware validator；如果 baseline 无法构造，应立即返回 UNKNOWN/错误，不应先报告 valid。

### S10-03：低层 `transition.Apply` 仍可绕过完整 S10 manifest 语义校验

- **严重度**：P2
- **位置**：`internal/transition/guards.go:328`、`internal/transition/engine.go:303`、`internal/controller/cycle.go:80`
- **当前实现**：正常 Controller 会先执行 Quality Gate；但低层 transition guard 主要验证当前 acceptance/release evidence、CleanRound 和文件 hash，不重新执行完整 manifest baseline/inventory 语义。
- **问题**：调用低层 API 的兼容/诊断路径，可能用结构上有效但未经过完整 S10 baseline 校验的 evidence 触发 TR-015/TR-017。
- **缓解因素**：文档明确禁止直接调用 `runtime transition`，正常自动路径已有 Quality Gate；因此这不是主路径当前绕过，而是低层 API 的防御深度不足。
- **建议**：将 S10 semantic gate 设为 TR-015/TR-017 的不可绕过 domain guard，或令低层 Apply 也强制调用同一 Quality Gate。

## 5. Blueprint 已明确的当前边界

以下项目属于未完全达到长期目标，但 Blueprint 已将其记录为当前实现边界，不能误报成隐藏的实现偏移：

| S9→S7 | Handoff 生成 ReviewPlan seed，Planner 还需审查；覆盖改变时 revise | 这是当前设计中的 staged seed，不是完整 S7 Plan |

## 6. 已确认对齐的部分

### S7

- ReviewPlan 注册前校验 coverage、Claim DAG、Assignment partition、N/A checklist、regression assets 和 frozen subjects。
- ReviewResult 对当前 plan、round、generation、subject digest、Claim set、producer independence 和 artifact digest 做绑定。
- CleanRound 使用严格 conjunction：当前 plan、完整 Claim disposition、当前结果、finding、证据新鲜度、blocking BUG、clean-round evidence 均需满足。
- 普通 Finding 会在当前 required work 完成后 drain；P0 可以提前 seal；S7 不把 targeted re-verification 当作完整 clean round。

### S8

- ObservationBatch → immutable InvestigationCase → Hypothesis/Result → causal closure → RepairContract 的主链已存在。
- intake 已校验 batch path/hash/schema、round/baseline 和 Finding exact set。
- `investigate_more`、`s2_spec_rework`、`s7_no_change`、duplicate 等路由已持久化并有 next action。
- Contract approval 不再依赖调查前创建 BUG；BUG 仅作为批准后的兼容投影。

### S9

- S9 只消费 approved RepairContract revision/hash。
- Session、Plan、PlanReport、Result、Changeset、ChangeImpact、TargetedReverification、RepairHandoff 均有不可变 artifact 和 Runtime CAS 绑定。
- PlanReport 有 red/blocked pre-fix check；execution begin 前有 first-write barrier。
- RepairResult 对 assignment exact unit、changed path+SHA、session-wide actual diff、scope deviation、migration/rollback 做校验。
- Targeted verifier 不能与原 assignment 相同；失败结果保留 typed recovery route；PASS 不会直接产生 CleanRound。
- Handoff 会清理旧 S7/S8 投影、记录新 baseline，并生成 staged S7 seed。

### S10

- acceptance/release-audit manifest 是机器事实源，Markdown 由 manifest 生成。
- 每个 inventory item 要求 source、expected、oracle、owner、disposition 和证据；counterevidence 与 inventory 一对一。
- release audit 要求八个 audit area。
- UNKNOWN、unsupported PASS、unowned risk、untracked debt、blocking finding 等指标会被重新计算，不信任作者填写的汇总值。
- 当前 manifest、证据 envelope、baseline、round 和文件 SHA 会在正常 Controller Quality Gate 中重验。
- S10 只推进到 S11/human release boundary，不直接执行发布。

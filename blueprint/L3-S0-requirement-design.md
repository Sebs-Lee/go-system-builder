# L3-S0 — 需求设计（Requirement Design）

> 层：第三层 ｜ 上游：L2 §S0 ｜ 机制事实经调查核实，含 file:line

## 1. 要实现什么

把人的意图固化成一份**人锁定的需求基线**——它是全链指纹的根：锁定后不可变，后续一切设计/契约/任务/证据都挂在它的指纹上。

- 进入时：人的意图陈述（对话），非结构化。
- 出去时：`docs/requirements/REQ-{id}.md` 状态=locked，含锁定记录（日期/操作人/版本）与可计算的 SHA-256——即 S1 `req bind` 的直接输入。
- 衡量：**锁定即冻结**——之后任何人（含 agent）改动它都必须走人的修订流程，且旧版本保持不可变（换 generation，不覆盖）。

## 3. 选了什么、为什么（含否决）

| 子问题 | 选用 | 否决与否决理由（减法） |
|:--|:--|:--|
| 怎么逼出完整需求 | 漏斗模板（推导式三层，字段即逼问）+ requirement-funnel skill（过程方法论，三分工：skill=过程、模板=结构、协议=路由） | 否决"模板逼问已够"——漏斗思考是过程方法论（怎么收敛、怎么上交），模板承载不了；也否决"访谈式替人提问"——把设计负担转移给人，只有清晰的方案交出去才有沟通意义 |
| 怎么管 UI 影响 | 顶部三值字段 + `parseUIImpact` 机械解析 + unknown 触发 guard | 否决"让 agent 自行判断何时补 UI 分析"——三值+guard 是零成本的硬地板 |
| 怎么防 agent 改需求 | human-only 锁定（bind 必须 `--approved-by`）+ 锁定写入拦截 + generation 不可变 | 否决"目录级静态保护"——运行时锁定清单才是对的粒度：锁前可自由草拟、锁后才冻结 |
| 怎么管锁定后修订 | change-control 规则（暂停 loop + 人批 + 新 generation） | 否决"就地编辑+版本号"——会破坏下游指纹链；换 generation 旧版永久可审计 |
| 怎么保证 REQ 质量 | 人 review（质量门=人闸本身）+ skill 身份互换自审（提议锁定前全审） | 否决"validate --all 扩展 REQ 检查"——bind 由人执行已骑在自然路径上（D2），机器复验人已把关的事是重复付费（公理四） |
| 自查清单形态 | 无 checklist——检查实质转为表格字段或下游引擎 | 否决"保留 checkbox 自查"——勾选=读过≠想过，且威胁模型错位（勾选者是人，人为后果负责且手握 bind） |

## 4. 怎么编排（时间线讲完一件事）

1. **意图进入**：人用自然语言表述预期效果（对话中，不落盘）——主会话载入 requirement-funnel skill 开始漏斗。
2. **§A 理念**：agent 把预期效果过一遍筛选（过滤口语歧义、补全隐含前提）整理成 A1，交人确认；随后起草 A2-A4/利益相关者/术语表——上交 §A 提案（≤3 个拍板点），人拍板。
3. **§B 方向与约束**：发散 2-3 个方向→剪枝到 1 推荐（被否方向记理由）→硬约束逐条验"必须性"→上交提案，人拍板。
4. **§C 具体需求**：FR 逐条挂"服务于 §A_"、流程与拒绝路径、验收标准、非功能、迁移清单、UI 影响表（顶部三值选一，unknown 允许——意图未明不必硬猜，S2 guard 会拦到 §D 澄清）→上交提案，人拍板。
5. **自审+锁定**：agent 身份互换全审（结论一段话入 §E）→ 人 review → 人给锁定拍板，agent 据此把顶部状态置为 locked 并在 §E 签锁定记录（日期/操作人/版本）。
6. **冻结生效**：此后任何写尝试触发 hook 硬阻断，恢复提示指向新 generation 目录；修订=暂停 loop（change-control）→ 人批 → g{N+1} 重锁（走同一漏斗）。
7. **交接**：S1 `req bind` 复核 locked/版本/指纹 → 入册。§F 覆盖矩阵骨架（REQ→BR→CASE→…→证据）此时埋下，是全链追溯的起点。

## 5. 期望效果

走完 S0：

- **意图有了不可变的锚**：锁定 REQ 是全链指纹的根（bind 后 generation+1，"never auto-promotable"）；
- **结构性防住**：agent 自创/自改需求（human-only 锁定）、锁定后漂移（写入拦截+generation 不可变）、"先实现后补文档"（change-control 禁令）、UI 影响含糊进设计（unknown guard）；
- **未知是安全的**：unknown 不会混过去，也不会阻塞发现——它显式登记在 §D，逼人在 S2 前澄清；
- **交给 S1**：locked 文件+锁定记录+SHA-256——绑定命令的三个直接输入。

## 6. 注意力预算与渐进披露

总评：S0 是人闸 stage——人 review + 人执行 bind 本身就是自然路径上的控制点（D2），质量失效另有 S5/S7 接盘。因此 S0 的设计立场是**质量门=人闸本身，机器只查状态**。判定尺见 L3-README「注意力分配原则」。

### 6.1 设计立场（为什么这样）

- 机器复验"人已把关的事"是重复付费（公理四）——bind 由人执行已骑在自然路径上，这些检查防的失效从未被观测；
- 模板必须是推导式三层而非扁平并列：需求是推导出来的（先理念、再方向与约束、再拆解），扁平结构把三类异质内容并列，填写者按节号填而不是按推导顺序想；
- 深度要求落进模板字段而非 checklist：填"回滚方式：__"而非勾"考虑过回滚"（D4 在 checkbox 上失效）。

### 6.2 阅读预算（谁在何时读什么）

| 角色 | 进入时必读 | 触发式加载（渐进披露） | 永不需要读（机制承载） |
|:--|:--|:--|:--|
| 主会话 | requirement-funnel skill + 推导式模板头部的漏斗指引（2 行）+ 当前层骨架 | §A 拍板后才设计 §B；§C 拆解时回看 §A 意图 | "锁定后不可改"——写入拦截当场告知；可绑定性——bind 拒绝时自解释 |
| 人 | 用自然语言表述预期效果（对话中给出，不落盘） | 确认 §A1 整理稿忠实于自己的意图；每层拍板点：方向取舍/范围边界/优先级等真价值判断（每层 ≤3 个） | 格式与完整性——模板结构+bind 状态检查的事；中度复杂度的设计决策——agent 全权接管并为设计负责 |

# 全局优化指南：确定交付、减负与执行流畅度

> 定位：模板全局优化的独立设计文档，位于四层主线之外，不属于 L4，也不新增层级。
>
> 状态：v0.1.0，2026-10-13。汇总本轮讨论的八类调优、交付机制优化和代码审查发现。建议尚需逐项实现与实战验收；文中明确标注已有基础，不把目标设计或隔离原型计为生产完成。
>
> 原则权威：[L1 设计原则](l1-principles/L1-design-principles.md)。本指南评价上下文、角色、任务、工具、环境、验证与调度的整体效果；具体生命周期和机制仍由 L2–L4 对应设计负责。安装后的项目和生产 Harness 不依赖本文件。

## 1. 目标与实战问题

实战中，Agent 可能早已完成自己的工作，却因为不知道还要填什么、登记什么、触发什么或等待谁而持续尝试。另一些迟滞来自过量上下文、模糊质量要求、任务耦合、重复验证和不稳定环境。优化需要覆盖整条交付链。

目标是让没有模板设计背景的执行者，只凭当前工作入口和必要工程资料，就能回答五个问题：

1. 我要交付什么，为什么需要它？
2. 当前已经具备哪些开工条件，我需要读什么？
3. 我现在能做什么，具体在哪里操作？
4. 怎样证明这项责任完成？
5. 交付是否已接收，下一步由谁负责，我能否结束？

机制应接近工程常识中的“领工单、准备材料、执行、验货、签收、交接”。实现、原型、提交和实际测试是工作；身份抄写、哈希拼接、重复信封和事件猜测应由机器承担。

优化以确定交付和质量为目标，同时减少无效阅读、重复工作、协调等待与人的持续干预。代码变少、Agent 变少、阶段变快或 gate 全绿，单独都不足以证明优化成功。

## 2. 全局约束

- Runtime、Assignment、冻结输入、领域记录和原门继续作为事实与权限来源；摘要、问卷、看板和本指南不构成第二套权威。
- 必要业务规格和源代码仍须阅读。减少流程手册依赖，不能变成不读工程输入。
- 机器公证事实，Agent 作专业判断，人承担既有需求锁定、发布和例外决定。JSON 形状合格不能证明业务正确，也不能制造人工授权。
- 写前计划、批准后的修复范围、独立审查、真实集成和 S9 后 fresh S7 等要求继续成立。
- 优化等待、拓扑或成本不能裁掉 required coverage，不能把未检查事项改成 N/A，不能复用不适用的旧 PASS。
- 先观测具体失败，再决定引导、结构或强制的落点。正常阶段未就绪时继续合法工作，不能把所有流程要求改成硬阻断。
- 达到当前责任的已声明收尾条件后交付；新增验证或扩展调查须对应具体风险、新证据或原有强制检查。

## 3. 现状与证据边界

### 3.1 已有基础

截至本轮代码审查，已经存在以下能力：

- Controller/Writer 的原门求值、单事件至多一次允许转换，以及 Runtime/journal 持久化。
- SessionStart/SubagentStart 的原生上下文注入与真实 Assignment 匹配。
- 普通 `plan_checkpoint` 的 PLAN_REPORT 消费、激活和继续执行自动链。
- 工作区 prepare/launch 的冻结输入、身份、角色和检查环境预检，精确操作命令与持久化集成 checkpoint。
- 部分 S7 错误的结构化 missing/repair/next/verify，以及指定 TeammateIdle 恢复提醒的同事实预算。
- Skill 中已写明最小上下文、重复检查须有理由、有效证据复用和交付后结束责任的行为要求。

实现依据见 [Controller](../internal/controller/cycle.go)、[生命周期上下文](../internal/hook/lifecycle.go)、[计划自动链](../internal/assignment/auto_chain.go)、[工作区启动](../internal/workspace/launch.go)、[工作区命令](../internal/cli/workspace_command.go)、[S7 诊断](../internal/review/gate_diagnostic.go)、[Idle 预算](../internal/hook/idle_budget.go) 与 [派发 Skill](../skills/agent-dispatch/SKILL.md)。

这些基础仍分散在不同入口。协议中的描述、代码中的能力和执行者实际收到的工作包，尚未形成完整的统一交付路径。

### 3.2 本轮发现与限制

- [Backend Builder](../agents/backend-builder.md) 声明 21 个预加载 Skill，[Frontend Builder](../agents/frontend-builder.md) 声明 16 个；包含不少特定技术和风险领域。这是配置事实，尚未实测对应 token、注意力或成功率影响。
- [AGENTS 模板](../AGENTS-template.md) 中“最短路径永远是最差工程决定”和“Unknown is unfinished”等措辞可能扩大审查范围；这是待验证的行为假设，本次未更改指令。
- [TASK 交付表](../docs/dev/tasks/TASK-template.md) 同列实现、测试、完成报告、DV、QA、E2E，角色说明则限制 Builder 的独立审查职责。模板呈现有职责歧义，不等于现有权限门已允许越权。
- [当前动作投影](../internal/cli/projection.go)、[阶段动作](../internal/cli/run.go) 与真实 gate missing 有不同生产路径。应逐阶段验证一致性；本次未复现所有阶段均有错误。
- [Hook 设置](../settings.json) 的 PostToolUse 不匹配 Write/Edit，现有 PostToolUse 也走观察路径。阶段答卷的保存消费尚未生产接线。
- [S5 隔离原型](../tools/stage-form-prototype/README.md) 验证了填写、局部错误、并行责任和回执等交互；它不证明真实 Hook、Git、身份、原门和崩溃恢复已落地。

详细机制依据参见 [阶段答卷](l4-mechanisms/L4-stage-form.md) 与 [手续收敛审查](l4-mechanisms/L4-procedure-reduction.md#12-协议要求到执行机制的覆盖审查)。本文件汇总全局优化方向，具体事务与路由契约引用其所属设计。

## 4. 八类调优 guideline

### G01 — 按任务选择技能与上下文

**Guideline：** 默认加载当前角色必需的少量基础能力，其他技能由实际技术栈、修改范围和风险触发。必需知识随作业送达，背景资料按需展开。

策略：

- 核对角色 frontmatter 与“最小上下文”要求的一致性，将稳定基础、技术栈专用、风险专用技能分开。
- 派发时根据已批准 TASK/Assignment 和实际项目技术栈选择技能；缺少必要信息时先补来源，不能仅凭模糊关键词自动判断适用性。
- 阅读清单给具体路径、必要章节、阅读目的与顺序；执行者不负责从多个全局目录重新构造阅读闭包。
- 当前上下文已有有效动作和产物身份时直接执行；重启、相关输入改变、失效或矛盾时刷新。
- 有界消息优先保留身份、当前动作、交付入口、收尾和等待责任；长范围、详细规范放进绑定的工作包。不能静默截断必要条件。

验收：记录输入 token、无关 Skill 加载量、重复阅读、首次有效操作时间；检查缩减后是否遗漏风险或提高返工率。不把“少读”单独作为成功标准。

### G02 — 质量指令给出范围、优先级与结束条件

**Guideline：** 质量要求绑定当前责任和已声明验收集合，执行者能明确知道何时继续、何时交付、何时移交问题。

策略：

- 将绝对化的效率否定改为有范围的工程要求：完成当前验收、处理具体阻断风险、达到收尾条件后交付；额外验证须有风险或证据理由。
- 区分当前责任内的未决事项、上游业务决定、系统故障和其他 owner 的待办。“Unknown”必须定位到具体断言及责任。
- 责任内影响验收的 UNKNOWN 仍是未完成；新发现的范围外风险登记并移交相应责任，不能静默忽略，也不能让单个 Worker 无限扩张调查。
- 原门/权限和具体 Assignment 的要求应清晰投影；发现冲突时提供维护路径，不让执行者凭措辞强弱猜优先级。
- 普通可回滚工程选择沿既有授权自主完成；涉及真正的人闸时明确等待已授权决定。

可采用的任务说明：

> 完成这份责任的交付与检查。发现阻断风险时记录证据并走对应路由；未决问题写明缺哪个决定、由谁决定。达到收尾条件后交付，不另开无具体理由的检查轮次。

验收：比较交付后的额外检查、范围扩张、重复确认和遗漏缺陷。本指南不直接更改 AGENTS 或减免已有门。

### G03 — 按上下文和耦合程度拆任务

**Guideline：** 每份任务可独立说明、执行和验收，任务粒度兼顾上下文容量与派发/集成成本。

策略：

- 规划时检查能否独立验收、是否依赖不同上下文、是否经常修改同一批文件。
- 共享大量资料或写入面的工作优先保持连贯；独立接口、输入和验收明确的工作再拆开。
- 每份任务声明真实依赖产物、写入范围和具体行为检查；不能仅靠一句短目标证明任务足够小。
- 记录任务完成前 compact、跨任务反复读同一资料、交接次数和冲突返工。过大时拆分或裁无关阅读，过碎时在保持追溯与覆盖的前提下重新规划。
- DAG 按实际依赖释放下一任务；独立慢任务不阻止已具备条件的后续任务。
- 已批准或冻结的任务调整仍走原规划/返工路径，不能在执行中悄悄合并或改范围。

验收：比较单任务上下文规模、交接占比、集成冲突、完成时间和返工；保留条款覆盖、依赖检查及独立职责。

### G04 — 项目惯例成为默认工程选择

**Guideline：** 普通工程选择优先沿用已批准设计与现有成熟实现；偏离时说明依据，真正的新业务决定明确移交。

策略：

- 从已批准设计与当前代码生成简短的项目惯例索引：错误处理、接口位置、状态归属、命名和测试结构等。
- 每条惯例附可定位的来源和真实示例；索引是可重建视图，原代码和正式设计保持权威。
- 明确存在多个惯例或正在迁移的情况，不能把“搜索到的第一个实现”自动封为标准。
- 正常任务给一个合适的参考实现，使执行者自然匹配项目写法；偏离惯例记录具体理由。
- 新决定在原权威产物中批准后，更新索引；会话记忆和无来源经验不形成新规则。

验收：比较例行实现选择中的迟疑/确认、风格偏离、架构返工；检查参考示例没有掩盖新的业务不变量。

### G05 — 验证证据可追踪、可判断是否复用

**Guideline：** 重复检查必须有明确理由。相同适用条件下消费已有有效证据，变化或独立性要求触发新检查。

策略：

- 检查回执记录实际代码树、命令、配置、环境、所覆盖用例、退出状态及日志，不能只记 pass。
- 再次请求检查时，工具展示已有证据与适用性；无法证明输入闭包一致时不能自动复用。
- 代码/配置/相关环境变化、中断、证据失效、新假设、独立审查和合并后验证，均可成为重跑理由。
- 局部改变按明确依赖关系失效受影响证据；已有领域要求的全模块回归或 fresh S7 继续执行。
- 不将候选树 PASS 当成合并树 PASS，不将作者检查当成独立结论；时间戳相同也不足以证明适用。
- 昂贵验证可以按既有配置选择执行位置和顺序；明确成本取舍及恢复依据，不默认减掉 required checks。

验收：记录检查耗时、重复原因、复用数量与失效正确性，配合遗漏缺陷与独立审查结果评估。

### G06 — 并行速度匹配接收能力

**Guideline：** 按真实槽位、共享资源、写入冲突和集成积压调节派发，优化通过集成的速度。

策略：

- 复用批准的 DAG、资源声明与现有派发看板，持续补位；容量不足时排队，required responsibility 不丢弃。
- 多个 Worker 已报告而 Main 接收积压时，优先集成并对新派发施加反压。
- 将共享文件或外部资源冲突纳入实际可并行判据，不以只读资料共享阻止两端并行。
- 普通小任务按协调收益选择 self/one_shot/单 Agent/团队；独立审查和 coverage-critical 责任按原分工执行。
- 正常等待、长检查和活跃 Worker 有明确 owner 与观测方式；不能从聊天沉默推断进程死亡或派出第二个 writer。

验收：观察在制任务、reported 积压、集成吞吐、交付后等待、冲突和返工；最大并行数不是单独目标。

### G07 — 检查环境提供稳定执行入口

**Guideline：** 依赖、运行方式、测试数据和日志由明确环境契约承载，执行者能区分环境失败与行为失败。

策略：

- 提供已解析的标准检查入口、启动条件、测试数据与必要资源约束；派发前检查适用平台与能力。
- 依赖和缓存按项目可复现要求准备，端口及可变外部资源按已登记资源处理。
- 环境不可用时返回具体条件和恢复 owner；不降级为任意 shell 或假通过。
- 工具返回命令、执行位置、退出状态、完整日志引用和失败类别；超时、中断和业务断言失败分别记录。
- 长执行用完成通知或有界观测，保留现场；固定等待和频繁轮询都不能代替进程状态。
- 仅依赖已验证的平台能力；真实平台验收与交叉编译/纯函数测试分开留证。

验收：记录环境失败率、搭建耗时、复现成功率、检查超时与日志定位成本，并验证中断恢复。

### G08 — 用实战案例和对照实验调优

**Guideline：** 将真实卡点变为可重放任务，每次只改变一个主要变量，在质量约束下比较行为与成本。

策略：

- 案例覆盖首次派发、缺输入、范围冲突、测试失败、已交未接、并行交付、compact、旧输入和环境恢复。
- 给新执行者当前作业包与必要工程资料，隐藏模板设计历史；不得把不读流程手册扩大为不读规格或代码。
- 对技能加载、指令措辞、任务粒度、参考示例、工具返回等分别进行对照；保留环境、资料和案例版本。
- 模型/推理预算按任务难度、风险、历史成功率和恢复成本评估，不只按前端/后端硬编码。配置实验需明确实验设置，不在普通任务中自行替换模型。
- 固定案例重复运行，并保留未用于调参的案例检验泛化；不凭一次演示声称稳定改进。
- 领域门测试、Hook 接线测试、真实平台运行与首次使用行为验收分别证明不同能力。

验收：同时比较首次交付合格率、遗漏缺陷、无效操作、延迟、token 和人工介入；没有实测结果的策略保持候选状态。

## 5. 贯穿交付链的优化策略

以下策略汇总前述讨论。它们是全局的交付体验与责任要求，具体接线仍落回所属机制。

### O01 — 发出可以开工的工单

派发前检查输入齐全、版本有效、依赖完成、工作目录可用、所需权限和检查环境就绪。工单给目标、必要输入、交付物、允许范围、收尾条件和失败去向。

缺业务决定归设计责任人，缺授权归相应闸口，缺环境归系统恢复。执行者不承担补齐隐含派发条件的猜测成本。写前计划尚未完成时，派发的是可执行的计划责任；产品写入仍受原屏障约束。

### O02 — 每项交付有唯一责任人

派发视图只要求执行者交自己的实现、测试或判断。后续 DV/QA/E2E、Main 集成与人工决定作为其他责任人的待办展示，不混进 Builder 必交清单。

例如：Backend Builder 交实现、自己的单元/集成测试及结果；Main 接收并完成集成；独立审查者提交各自结论。全局阶段缺口不自动变成当前 Worker 的欠项。

### O03 — 用行为样例和实际检查确定验收

工单从已确认契约提供关键行为的正常、失败和边界例子，并尽量绑定实际检查。例如导出功能：有权限返回固定列序 CSV；无权限返回 403 且不创建导出任务；无数据返回只有表头的 CSV。

样例帮助确定方向，独立审查继续判断覆盖和遗漏风险。未决定的业务行为必须形成明确问题及 owner，不能由测试生成器或执行者自行补成规格。

### O04 — 直接提供有效操作与权限

角色、scope、activation、Runtime 和策略的交集由系统解析，给出实际 cwd、允许路径、当前写前条件、提交入口和参数完整的命令/argv。

错误说明哪个条件未满足以及恢复责任。内部 TR、PTR、phase 和事件名保留用于运行与诊断；正常入口使用“读、实现、检查、交付、接收”等工程动作。

### O05 — 注册 JSON 问卷并在自然保存路径接收

模板同时注册字段形状、题目、枚举含义、条件、示例、阅读目的和具名消费者。已知字段由系统填写，专业判断给 null 或明确空位；通过时 findings 为 []，失败时要求可定位的观察。

每个执行者填写独占输入，Writer 汇总；保存后校验真实 owner、冻结输入和当前适用性，再调用原领域 API、求原门、返回回执。计划和最终结果按原先后分别发题。人类授权消费明确决定，不能从文件存在或 Agent 写 approve 推断。

JSON 接收不等于所有业务检查通过。无 Hook 环境使用已支持的宿主消费入口；只有文件落盘的环境明确标为未自动接线。S5 原型和生产链路分开验收，详见 [阶段答卷](l4-mechanisms/L4-stage-form.md)。

### O06 — 真实产物自动生成手续与重复载体

工具捕获修改路径、提交、检查与退出码、产物引用、版本和摘要，派生原证据信封、消息、报告及兼容投影。执行者补专业判断与理由，已有事实通过引用复用。

通用计划和领域计划中的相同事实共用来源，只询问领域新增判断。两个记录仍满足各自消费者，最终 completion 不能追认写前计划。

### O07 — 拒收给出最小修正范围

反馈给具体字段/证据位置、期望、实际值、修正动作和责任人。已有有效回答保留，相关输入变化才按依赖失效；不要求因一个空字段重填整卷。

实际门缺口如果不能映射到题目、真实交付条件、人决定或系统待办，登记 adapter/模板缺陷并移交维护，不让业务 Agent 阅读 Harness 源码猜补法。

### O08 — 自己完成、阶段完成与系统恢复分别呈现

接收回执至少说明责任状态、work_complete、当前阶段、waiting_on、next_owner 和当前动作。本人已接收、只等其他 owner 时，可以结束；有确实属于本人的后续责任时，才保留明确等待。

Worker 的实现结果已接收、Main 尚待集成时，阶段可以仍在 S6。产品提交与真实集成仍是全局交付条件，不能用 completed 字段替代。

### O09 — 交接形成持久待办并可恢复

接收后将后续责任写入原持久化记录/检查点，由调度器派发或 Main/Integrator 接续。响应丢失、消费中断和下一卷生成失败时，重建当前回执和待办。

相同输入幂等消费，修订保留历史与 supersedes；旧轮、旧 owner 或旧基线不能污染当前 PASS。单事件最多一次允许迁移，长测试和合并不塞进短 Hook。复用原事务与恢复入口，不在持锁事务内递归调用 Writer。

### O10 — 猜测与重试有明确出口

可修正错误有新修改后重交；缺业务决定提出具体问题并移交；环境/接线故障形成系统恢复待办。同作业、同失败和相同相关输入反复出现，没有新修改或区分性证据时，停止重复动作并诊断原因。

无进展预算不把未完成改成完成，不取消安全门，也不把正常长运行或等待其他 owner 当成死循环。恢复继续保留原 Assignment 与现场，不盲目替换 Worker。

### 6.1 “提醒已经落地”的判定

每项必须遵守的协议要求，在设计与测试中可追溯以下五个落点：

1. **生产者**：谁提供题目、事实、条件或具体动作？
2. **送达事件**：在哪个真实工作入口或工具返回中送到执行者？
3. **消费者**：哪个原领域 API、门或责任人消费交付？
4. **失败归属**：缺输入、判断失败、系统故障分别由谁处理？
5. **接续与验收**：通过后谁接棒，哪项实际入口测试证明这条路径成立？

只有文档或输出字符串记为指导/部分实现。系统已知事实由 adapter 自动生成；实际先决条件由预检/原门保证；专业判断由题目、资料、证据与独立责任承载。上述落点供维护者检查，不增加 Agent 必填登记表。

## 7. 观测指标与实验方法

| 指标 | 口径与用途 |
| --- | --- |
| 首次交付合格率 | 首次完整提交被原消费者接受的作业比例；草稿保存不计完整提交，并按拒收原因分类 |
| 首次有效操作时间 | 从作业可开工并送达到首次产生交付内容或区分性证据的时间；单纯查状态不算 |
| 流程查找次数 | 为找操作格式、事件、身份或 Schema 查手册的次数；必要业务阅读单列 |
| 重复阅读/加载 | 相同相关输入未变时的重复读，以及与任务无关的 Skill 加载 |
| 无变化重试 | 同作业/缺口无新修改、输入或证据时的重试；合法长运行观测单列 |
| 检查重复成本 | 按重跑理由统计命令次数和耗时；独立/合并后检查单列 |
| 保存到接收延迟 | 完整交付保存到持久接收/拒收回执的时间；阶段转换和长集成延迟分别统计 |
| 交付后滞留 | 本人责任已接收到结束责任的时间，以及被重复要求交付的次数 |
| 调度与接收积压 | 实际 WIP、reported 待集成数、等待时间、集成吞吐及冲突返工 |
| 环境与恢复 | 环境失败率、复现成功率、中断恢复时间及重复执行副作用 |
| 质量约束 | 原 required coverage、遗漏缺陷、独立审查发现、失效/旧证据误用、越权与人闸边界 |
| 总成本 | 按角色/任务统计 token、工具调用、等待、检查、重做和人工介入；不能只比较模型单价 |

先取得固定案例基线，按失败类型和入口分组，每次改变一个主要变量，再用未参与调参的案例复验。保存案例、版本、配置、平台与运行结果；报告分布和失败原因，不只给一个平均数或演示视频。

不能靠放宽门、缩 required set、自动补 PASS、取消独立性或把人决定改为推断来改善数字。缓存与证据复用须证明当前适用；成本下降伴随遗漏风险升高时，不视为通过。

## 8. 建议实施与实验次序

| 次序 | 范围 | 完成证据 |
| --- | --- | --- |
| 1 | M02/M04/M05：真实缺口归 owner、责任回执、交付触发接收 | S5 的真实派发→交付→原门→路由/等待/恢复闭环；已完成者无无关操作也能结束 |
| 2 | M01/M03/M06/M07：可直接执行的工作包与精确修正 | 首次使用不查流程格式；长上下文仍保留入口；字段错误只修必要内容 |
| 3 | G01/G02/G04：按需加载、有界质量指令、项目默认惯例 | 固定案例对照，阅读/额外检查/例行确认减少且质量约束保持 |
| 4 | G03/G06：任务粒度、依赖释放、按积压调度 | compact、交接和冲突改善，接收吞吐提升，required coverage 不变 |
| 5 | G05/G07 与 M08/M09：证据适用性、执行环境、无进展诊断 | 失效/漂移/独立性矩阵、中断恢复及不同入口/平台验收 |
| 贯穿 | G08/M10：实战案例、行为与成本观测 | 每项改变有基线、对照、质量结果与平台边界，效果未经验证仍标候选 |

顺序是优化建议，不替代原生命周期。每个具体改动仍在所属角色、模板、Skill、领域 API、Hook 或测试中实施；本文件不创建第二调度器、第二状态机或新的例行手续。
